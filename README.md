
## Streamlit画面の実行（今回追加）

リポジトリのルートで実行します。

```bash
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .streamlit/secrets.toml.example .streamlit/secrets.toml
```

`.streamlit/secrets.toml` の `GEMINI_API_KEY` と `SPREADSHEET_KEY` を実際の値に置き換えてください。シートIDはGoogle SheetsのURLの `/d/` と `/edit` の間です。`WORKSHEET_NAME` は空欄なら先頭のシートを使います。

認証には次のどちらかを使います。

- ローカル：Secretsの `[gcp_service_account]` テーブル全体を削除し、既存のルートにある認証JSONを使用。別のファイルなら `GOOGLE_APPLICATION_CREDENTIALS` 環境変数でパスを指定。
- Community Cloud：認証JSONの対応する値を `[gcp_service_account]` に転記。秘密鍵は複数行のまま保持。

Google CloudでSheets APIとDrive APIを有効にし、対象スプレッドシートをサービスアカウントの `client_email` に閲覧者として共有してください。実際の認証情報・APIキーはGitHubに登録しません。

```bash
python -m streamlit run streamlit_app.py --server.headless true
```

表示されたローカルURLを開き、経験と希望を入力して「キャリア診断開始」を押します。求人データを取得してGemini `gemini-3.8-flash`で診断し、結果を画面に表示します。診断は送信時だけ実行されます。診断結果はユーザーごとのセッションに保持され、Sheetsには書き込みません。入力内容と求人の統計・サンプルはGemini APIに送信されます。

月給と契約月単価は入力時に区別します。求人の月給を12倍した換算年収は賞与を含まず、契約月単価を直接評価する指標ではありません。

### Community Cloudへ進むとき

1. GitHubリポジトリに `streamlit_app.py`、`src/career_advisor_rag.py`、`requirements.txt`、`.gitignore` などを登録します。`.venv`、`secrets.toml`、認証JSONは登録しません。
2. Community CloudでGitHubリポジトリとブランチを選び、起動ファイルに `streamlit_app.py` を指定します。
3. Advanced settingsのSecretsに、実値を記載したSecretsのTOMLを設定します。Cloudでは `[gcp_service_account]` が必要です。Pythonはまず3.12で確認してください。
4. デプロイ後に入力・Sheets取得・診断結果表示を確認します。

公式手順：https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/deploy

定期スクレイピングの実行設定は今回の追加には含みません。画面は蓄積済みのSheetsを読み込みます。`requirements.txt` は診断画面用の依存関係です。

## ⚠️法的リスクの境界線、セキュリティ、利用規約について

100件×30〜40技術となると、全体で約3,000〜4,000件（100〜200ページ分）のリクエストになります。この規模になると、対策なしで実行した場合は確実にセキュリティ検知（IPブロック）や利用規約上の問題に直面します。

技術的・法的なリスクの境界線と、それを完全にクリアして安全に運用するための具体的な戦略を整理しました。

---

### 1. 法的リスク（著作権・動機・サーバー負荷）

日本におけるスクレイピングの法律（著作権法第30条の4など）において、以下の3点がポイントになります。

* **データの利用目的（合法）**: 情報を「分析・統計（市場データの集計）」に利用する行為は法的に認められています。取得した求人文面をそのままコピーして自社サイトに無断転載（デッドコピー）しない限り、著作権法上の問題は極めて低いです。
* **利用規約（私的利用と契約）**: 多くの求人サイトは利用規約で自動収集を禁止しています。規約違反自体は直ちに刑法上の罪になりませんが、「サイト側に過度な負荷をかける行為」は電子計算機損壊等業務妨害罪（偽計業務妨害）に問われるリスクが生じます。
* **結論**: 「サーバーに迷惑をかけないスピード（人間と同等以下のアクセス頻度）」を厳守していれば、法的なトラブルに発展するリスクは極めて低くなります。

---

### 2. 技術的セキュリティ（IPブロック・WAF）

求人ボックス（カカクコムグループ）のような大型ポータルサイトは、Cloudflare等のWAF（Web Application Firewall）を導入しています。

* **検知されるトリガー**:
1. 機械的な一定間隔（例: 正確に2秒おき）でのアクセス
2. 短時間での大量リクエスト（例: 1分間に数十リクエスト以上）
3. ブラウザ固有の挙動（Cookieの非保持、特定のヘッダー欠落）の不自然さ


* **ブロックされた場合**:
IPアドレスがブラックリスト入りし、403エラーやCAPTCHA（「ロボットではありません」の認証画面）が返ってくるようになります。

---

### 3. セキュリティにかからず迷惑をかけない「ベストな運用設計」

100件/技術（1技術あたり約3〜4ページ、30技術で約100〜120ページ）を安全に巡回するための設計ルールです。

#### ① 「1回で一気にやらない」分散実行スケジュール

全30技術を1回のプログラム実行で叩くのではなく、**「1時間に5技術ずつ」など cron（定時実行）で分散**させます。

| 項目 | 設定値の推奨例 |
| --- | --- |
| **ページ間スリープ** | `random.uniform(4, 8)` 秒 |
| **技術（キーワード）間スリープ** | `random.uniform(30, 60)` 秒 |
| **1回の実行での取得上限** | 5〜10技術（約20〜40ページ分） |
| **全体スケジューリング** | 1日の中で数回に分けて分散実行（深夜〜朝方を推奨） |

#### ② 失敗を検知したら「即時撤退（冷却期間）」するロジック

ブロックを回避する最大のコツは、「ステータスコード異常を検知したらその日のスクレイピングを即座に中止する」ことです。しつこくリトライするとIPブロックが長引きます。

```python
# 応答チェックの例
if response.status_code in [403, 429]:
    print("⚠️ アクセス制限の可能性を検知。処理を安全に緊急停止します。")
    # 管理者へ通知を飛ばして sys.exit() などで即終了する

```

#### ③ クロール用の専用サーバー（VPS）を用意する

自宅やオフィスのIPアドレスでブロックされると業務に支障が出るため、スクレイピング実行環境は AWS (EC2) や ConoHa VPS、さくらのVPS などの**クラウド環境上に隔離**して運用するのが鉄則です。

---

### 4. まとめ：実装時のチェックリスト

1. **アクセス速度**: 1リクエストごとに 5 秒前後のランダムな空き時間を確保しているか？
2. **分散化**: 30技術の取得を 6時間〜1日かけてゆっくり巡回する構造になっているか？
3. **安全装置**: 403 / 429 エラーが出たら、即座にプログラムが自爆（ストップ）して冷却期間に入るようになっているか？

この設計を守っていれば、相手サーバーへの負荷は「人間がゆっくりブラウザで検索してページをめくっている程度」に抑えられるため、IPブロックや法的リスクを回避して安全に運用可能です。
